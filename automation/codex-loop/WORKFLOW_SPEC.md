# tmux 기반 Codex Sol 6.1·Terra 자동 구현·검수 흐름

## 1. 목적

사용자가 오류 위치를 직접 찾거나, 검수 결과를 모델 사이에 반복해서 복사·붙여넣기하지 않도록 다음 작업을 연결한다.

**하네스가 작업 전달 → Sol 6.1이 구현 → Terra가 독립 검수 → Sol 6.1이 수정 → Terra가 재검수 → 통과하면 다음 작업**

이 파일은 실행 흐름과 작업 규칙을 정리한 문서다. 자동 실행을 하려면 두 Codex 세션을 호출하고 결과를 전달하는 연결 스크립트 또는 같은 기능을 제공하는 하네스가 필요하다.

## 2. 각 구성요소의 역할

| 구성요소 | 역할 |
| --- | --- |
| tmux | 여러 터미널 작업 창과 세션을 유지하고 표시한다. |
| 하네스의 연결 스크립트 | 작업 전달, 실행 종료 확인, 결과 저장, 다음 단계 호출, 반복·중단을 제어한다. |
| Codex Sol 6.1 | 기능명세서에 따라 구현하고, 오류를 수정하고, 테스트를 실행한다. |
| Codex Terra | 원래 요구사항과 구현 결과를 대조하고, 직접 실행해 오류를 재현하고, 수정 계획과 검수 결과를 작성한다. |
| 기능명세서·문제 원문 | 무엇을 구현하고 어떤 결과를 내야 하는지 정하는 기준이다. |
| 테스트·브라우저 검사 도구 | 실제 입력·출력, 사용자 행동, 프론트·백엔드 연결 결과를 검사한다. |

tmux를 설치하는 것만으로 Sol과 Terra 사이의 자동 전달이 설정되지는 않는다. 기존 하네스가 AGENTS.md와 스킬 파일만 제공한다면, 자동 호출·결과 전달 기능을 별도로 추가해야 한다.

## 3. 전체 실행 순서

| 순서 | 담당 | 수행할 작업 | 다음 단계에 전달할 내용 |
| --- | --- | --- | --- |
| 1 | 하네스 → Sol 6.1 | 기능명세서와 이번 작업의 범위·완료 기준을 전달한다. | 원래 요구사항, 작업 범위, 완료 기준 |
| 2 | Sol 6.1 | 기능을 구현하고 관련 테스트와 기존 테스트를 실행한다. | 변경 내역, 실행 명령, 테스트 결과, 남은 문제 |
| 3 | 하네스 → Terra | 같은 작업의 기능명세서, 현재 코드, Sol의 실행 결과를 전달한다. | 검수 대상 코드 버전, 요구사항, 실행 기록 |
| 4 | Terra | 요구사항을 대조하고 직접 실행해 오류를 재현한다. 실패한 항목의 수정 계획을 작성한다. | 통과·실패·미검증, 재현 방법, 기대 결과, 실제 결과, 증거, 수정 계획 |
| 5 | 하네스 → Sol 6.1 | 실패한 항목과 Terra의 수정 계획을 전달한다. | 재현 가능한 실패 사례와 수정 우선순위 |
| 6 | Sol 6.1 | 오류를 재현하고 코드를 수정한다. 관련 테스트와 기존 테스트를 다시 실행한다. | 수정 내역, 실행 명령, 실제 결과, 해결되지 않은 항목 |
| 7 | 하네스 → Terra | 수정된 최신 코드에 대한 재검수를 요청한다. | 수정 후 코드 버전과 수정 결과 |
| 8 | 하네스 | 필수 항목이 통과하면 다음 작업으로 진행한다. 실패하면 5번으로 돌아간다. | 다음 작업 또는 남은 실패·미검증 보고 |

Sol이 구현을 끝내면, 같은 작업에 대한 Sol의 수정을 잠시 멈춘 상태에서 Terra가 검수한다. Terra 검수 중에 검사 대상 코드가 바뀌면 해당 결과를 무효화하고 최신 코드로 다시 검사한다.

## 4. Sol 6.1의 수정 단계에 넣을 지시

> Terra의 검수 결과와 수정 계획을 읽어라. 실패한 항목을 같은 조건에서 먼저 재현하고, 원인을 확인한 뒤 필요한 코드를 수정해라. 관련 테스트와 기존 테스트를 다시 실행하고, 수정 내역·실행 명령·실제 결과·남은 문제를 하네스에 전달해라. 완료 판단은 수정된 최신 코드에 대한 Terra의 재검수 결과로 한다.

수정할 때 지킬 규칙:

- Terra의 수정 계획은 제안이다. 코드와 실행 증거를 확인하고, 근거가 다르면 이유를 기록한다.
- 요구사항을 임의로 바꾸거나 기능을 제거해서 검사를 통과시키지 않는다.
- 검사 통과를 위해 테스트를 삭제하거나 기대값을 실제 오답에 맞추지 않는다.
- 수정한 기능뿐 아니라 기존 핵심 기능도 다시 검사한다.
- Sol 자신의 테스트가 통과해도 Terra의 재검수를 거친다.

## 5. Terra의 검수 단계에 넣을 지시

> 원래 문제와 기능명세서에서 검사 항목을 도출하고, 실제 프로그램을 실행해 기대 결과와 비교해라. Sol의 완료 보고만으로 통과시키지 마라. 오류 위치·원인·로그를 사용자에게 찾아오라고 요구하지 말고, 접근 가능한 코드·테스트·브라우저·서버 로그에서 직접 조사해라. 실패하면 재현 순서, 입력, 기대 결과, 실제 결과, 증거와 수정 계획을 작성해 하네스에 전달해라. 실행하지 못한 항목은 미검증으로 표시해라.

검사 항목은 원래 요구사항과 알려진 정답에서 도출한다. Sol이 만든 테스트만 재실행하는 데 그치지 않고 누락된 조건도 확인한다. Terra가 정한 기대값 역시 틀릴 수 있으므로, 중요한 값은 공식 예시·신뢰할 수 있는 기준과 대조한다.

원하는 동작이 불명확할 때는 임의로 정답을 만들어 통과시키지 않고, 모호한 조건만 사용자에게 확인한다.

## 6. 프론트·백엔드 연동 검사

Terra는 실제 백엔드의 요청 주소, 요청 방식, 입력 필드, 응답 구조, 인증 방식, 오류 처리를 확인한다. OpenAPI·Swagger 문서가 있다면 활용하되 실제 실행 응답과 대조한다.

기능 하나씩 다음 흐름을 확인한다.

**사용자 입력·버튼 클릭 → 실제 API 요청 → 서버 처리 → 화면 반영 → 필요한 경우 저장 결과 재조회**

게시판의 저장 기능이라면 다음을 확인한다.

1. 화면에서 글을 입력하고 저장한다.
2. 실제 백엔드에 올바른 요청이 전달되는지 확인한다.
3. 서버의 응답과 화면 표시가 일치하는지 확인한다.
4. 다시 조회하거나 새로고침해도 저장한 글이 유지되는지 확인한다.
5. 잘못된 입력이나 인증 실패도 명세대로 처리되는지 확인한다.

브라우저 실행이 가능한 환경이면 Playwright 같은 도구로 사용자 행동과 요청·응답을 검사한다. 가짜 응답으로 화면을 확인한 결과는 실제 백엔드 연동 검증과 구분한다. 필요한 서버·브라우저·계정을 사용할 수 없다면 해당 항목은 미검증이다.

## 7. 검수 결과 형식

| 필드 | 기록할 내용 |
| --- | --- |
| 요구사항 ID | 어떤 요구사항을 검사했는지 식별할 값 |
| 코드 버전 | 검사 대상 코드의 버전·해시 등 식별 정보 |
| 판정 | 통과 / 실패 / 미검증 |
| 재현 방법 | 실행 명령 또는 사용자 행동 순서 |
| 입력 | 실제로 사용한 데이터·조건 |
| 기대 결과 | 요구사항에 근거한 올바른 결과 |
| 실제 결과 | 실제 실행에서 확인한 결과 |
| 실행 증거 | 테스트 출력·서버 로그·브라우저 기록 등의 위치 |
| 수정 계획 | 원인 근거, 필요한 변경, 수정 후 재검사 항목 |

판정의 의미:

- **통과:** 실제 실행 결과가 정한 기준과 일치한다.
- **실패:** 실제 실행 결과가 기준과 다르다.
- **미검증:** 실행 불가, 접근 불가, 기준 불명확 등의 이유로 확인하지 못했다.

모델이 작업을 끝냈다는 사실이나 실행 프로세스가 종료됐다는 사실만으로 기능 통과를 결정하지 않는다. 검사한 항목이 없는 실행이나 필요한 검사를 건너뛴 실행도 완료로 인정하지 않는다.

## 8. 반복·중단·다음 작업 진행 조건

### 다음 작업으로 진행하는 조건

- 해당 작업의 필수 요구사항별 검사가 실제 실행됐다.
- 수정된 최신 코드에 대한 필수 검사가 모두 통과했다.
- 필수 항목에 실패나 미검증이 남아 있지 않다.
- 실행 기록과 검수 결과가 남아 있다.

### 수정·재검수 반복 조건

- 실패한 항목이 있고, 현재 환경에서 수정과 재검사가 가능하면 Sol에 수정 작업을 전달한다.
- 기본 예시로 최대 3회의 수정·재검수를 허용한다. 실제 횟수와 시간 예산은 시험 제한에 맞게 정한다.

### 중단하고 보고하는 조건

- 정한 횟수나 시간 제한에 도달했다.
- 같은 실패가 반복되고 진전이 없다.
- 요구사항 결정, 계정, 권한, 외부 서비스 등 사용자의 추가 정보가 필요하다.
- 필요한 검사를 실행할 수 없어 필수 미검증 항목이 남았다.

중단 시에는 완료라고 보고하지 않고, 남은 실패·미검증과 필요한 다음 조치를 정리한다. 전체 통과는 검사한 요구사항과 조건의 범위에서 통과했다는 뜻이며 모든 가능한 오류가 없다는 보장은 아니다.

## 9. 실제 구성 전에 확인할 사항

- 시험 환경에서 tmux와 Codex 별도 세션 실행을 사용할 수 있는지 확인한다.
- Sol 6.1과 Terra의 실제 선택 가능 여부와 모델 식별자를 확인한다.
- 두 세션이 같은 검수 대상 코드와 요구사항에 접근할 수 있게 한다.
- 하네스에 자동 호출·결과 전달 기능이 있는지 확인하고, 없으면 연결 스크립트를 작성한다.
- 실행 명령, 테스트 명령, 서버 주소, 필요한 환경 설정을 실제 프로젝트에서 확인한다.
- 검수 결과를 자동 전달할 때는 정해진 필드와 실행 결과를 사용하고, 자유로운 문장의 ‘완료’ 표현만으로 분기하지 않는다.

이 문서 자체가 연결 스크립트를 대신하지는 않는다. 자동화 구성 후에는 작고 의도적으로 실패하는 사례를 사용해, 실패 감지·수정 전달·재검수가 실제로 이어지는지 먼저 확인한다.
